# 从敌方角色偷取生命上限

后续真实丑恶的残躯现已接入：原水蛭每个实际主体查询同控制者当前有效残躯，每份增加1点，原角色生命转移执行器保持。复制、沉默、转控及整组召唤受益边界见[后续契约](m3-summon-group-bonus.md)；下文首次接入时的“未来来源”说明保留为历史。

真实依赖是EDR_817血虫感染所召唤的EDR_810t饱胀水蛭。固定卡面写明：本人回合结束时，由英雄从当前生命值最低的敌人偷取1点生命。完整源行与脚本数值保存在`data/cards/native-followup-effects-v1.json`；它不是普通伤害或吸血。

`hs_sim.engine.health_theft`提供两个有限公共请求：

| 请求 | 输入 | 行为 |
| --- | --- | --- |
| `StealHealthToHero(player_id, donor, amount, source_id)` | 普通随从的`MinionReference`或英雄物理ID | 原对象仍合格时，将其生命上限转给执行时本方当前英雄 |
| `RandomStealHealthToHero(player_id, candidates, amount, source_id)` | 不重复的原物理引用元组 | 对仍合格的原候选等权选择一次，再交同一个转移请求 |

整数引用只允许英雄，并须仍是原物理英雄；随从沿原区域/卡面/控制者/驻留守卫，不在等待后绑定同名新实体。对象须存活、未标记消灭且为敌方角色；普通随从排除休眠和特殊交互物体。严格校验来源，即使原池为空也不能接受不存在的来源。零量不分配属性附件或消耗随机数；空池和单项不取随机数，并列原物理候选只抽一次。随机反应后的目标失效则跳过，不改选。

选择最低生命由卡牌的纯主体完成，比较当前剩余生命，英雄与随从都参与；不按生命上限、护甲或攻击筛选。每个实际结束主体通过命名`InvokeBehavior`在执行时重新读取场面，因此后一个水蛭可看到前一个的死亡结果。接受及重复仍归原结束窗口；这里没有新结束时钟或排序器。

转移数量沿原英雄转移政策，取请求量与提供方当前生命上限的较小值；两方保留缺失生命。英雄之间直接委托原`StealHeroHealth`。随从减少生命复用原`Buff(health=-amount)`，英雄增加上限复用原`adjust_max_health`：先提交英雄但暂不发布，随后提交随从，再发布原两类事件。首个触发捕获已能看到双方结果，死亡检查和反应继续由原解释器处理。没有新伤害、治疗、生命支付或替换入口，没有新状态账本、保存字段或公开事件种类。

内部政策将随从的减生命作为普通可沉默附件，英雄取得的上限作为永久不可沉默附件；原来源死亡不回收已转移数值。圣盾、免疫、护甲及伤害/治疗层不截获属性转移。回手、变形、复制、死亡和英雄替换沿各自已有属性生命周期。本轮数值/生命周期政策由core318签名保护，schema268布局保持，旧布局不能据此自动认证。

社区对局报告支持“降低最大生命、普通治疗不能补回、绕过护甲”的可见表现。[玩家实测讨论](https://us.forums.blizzard.com/en/hearthstone/t/unable-to-heal-up-my-hero-all-of-a-sudden-during-a-game/154552) 另有实际受伤随从被第一只水蛭杀死、第二只仍异常作用于原目标的报告，说明应单独核对主体执行窗及原对象身份。[2026年问题报告](https://us.forums.blizzard.com/en/hearthstone/t/bloated-leech-broken/158667) 这些不是国服精确服务器测量；并列RNG、超过剩余生命的转移量、随从沉默、准确归因和结束顺序仍须M6校准，不能把内部一致性当作官方确认。

隐藏的原物理引用和待执行工作只进入内核快照，玩家仍通过原角色投影与已允许的属性事件观察结果。当前入口不预先开发水蛭额外数值来源；真实Hideous Husk等后续卡牌接入时按有效卡面扩展，不将其当白板或从正式应有池中删除。实际进度、验证与下一项仅维护在项目状态和机制清单。
