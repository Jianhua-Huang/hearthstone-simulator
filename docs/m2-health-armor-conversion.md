# 英雄实际生命转护甲

真实需求为BE_558石头护手：1费2攻2耐久战士武器，在本人英雄攻击后将5点生命转为护甲。完整原行与两语言完整官网面保存在`data/cards/health-armor-conversion-v1.json`；正式资格、国服精确语义及热修仍独立验收。执行进度和下一项仅在原两份台账维护。

## 原攻击入口

薄适配器复用`completed_attack`，只响应完整`attack_finished`所绑定的原完成英雄攻击、原玩家及原武器实体。随从、对手、取消或只有声明的攻击不转化。最后耐久消耗后的原武器续接沿既有武器/攻击生命周期，不以当前装备槽重找来源。

## 两次原数值提交

`ConvertHeroHealthToArmor(player_id, amount, source_id)`位于既有`health_loss.py`，只接受已知物理来源、合法玩家和非负整数。执行时读取本人当前存活且未待销毁的已安装英雄，调用原`LoseHealth`执行EFFECT生命损失，立即保存本次剩余生命实际减少量，再调用原`GainArmor`增加同量护甲。两次原数值提交在正常检查点前完成，不创建新账户、损失执行器、费用用途或可变计数。

原生命损失不经过伤害修正、护甲吸收、免疫、圣盾或吸血，现有显式EFFECT下限及生命损失替换仍适用。替换造成增长或实际减少为零时不凭请求量增加护甲；明确下限只减少两点时也只增加两甲。没有声明的下限不会凭空保护到一点生命，普通可致死损失仍交原英雄致死协调，护甲不能救回零或负生命。此处低生命、替换及转换方式是明确的内部政策，仍待M6国服校准，卡面本身不能证明这些精确边界。

## 反应、恢复和信息

实际变化在原数值提交中冻结，后续治疗、护甲消费、英雄变化或等待不重新计算原转换。原`health_lost`、英雄生命过渡与`armor_gained`及增甲账本保留各自语义；数值提交与捕获事件按原解释器反应顺序继续，损失通知捕获时尚未提交随后护甲，正常检查点已完成两次数值提交。精确通知及反应窗口仍待校准。
