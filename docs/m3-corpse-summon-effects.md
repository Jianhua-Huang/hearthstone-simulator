# 原残骸支出与固定召唤交付

上一张使用的印刷符文用原冻结历史查询；固定召唤组从完整原交付连接原目标强制攻击，保存、容量与时序边界见[符文与召唤组战斗契约](m3-blood-rune-native.md)。

原随从残骸门禁在执行时重核实际来源、空位/复生/召唤对象，再沿原完整支付分支；原目标伤害与三个真实选项保持引用和信息边界，见[残骸触发与选择契约](m3-corpse-trigger-choices.md)。

本契约描述投喂加餐、坟墓守卫、白骨卫士指挥官和亡者大军的有限表达。实际执行、验收、差异和下一项仍仅在[项目状态](project-status.md)与[机制清单](mechanism-backlog.md)维护。

## 固定来源与两类原生入口

`Registry.register_corpse_summon_profile(CorpseSummonProfile)` 登记真实根卡、固定随从、数量及两种模式。`grant` 是固定召唤完成后支付完整残骸阈值并授予突袭/复生；`raise` 是将有界实际支出换成同数量的固定召唤。前者仅普通法术，后者允许普通法术和真实随从战吼。不可变声明进入注册表指纹；未声明的默认规则包保持原指纹。不增加任意回调、CardDefinition 字段或新的资源执行器。

原生主体保留实际 `RuleContext.cast` 或 `battlecry` 的身份、来源及玩家。普通召唤白骨卫士指挥官不会触发战吼；真正重复战吼每次独立接受新的局面、余额和空位。自动法术的实际物理法术来源与调用方 `caster_id` 分开，不能把调用方当作支付来源。

## 先召唤、后完整阈值奖励

投喂加餐先发出五个原归因饥饿幼龙请求，坟墓守卫发出两个原归因凶恶僵尸请求，再执行 `ResolveCorpseSummons`。到达该窗口后才读取实际残骸余额，包含此前召唤及其反应带来的变化。余额不足不部分扣除；足够时沿原 `SpendUpToResource` 做一次有来源的固定全额消耗。

`original_summon_groups` 从原完整 `SummonCause`、固定材料和要求数量连接每个原生产根，再连接其实际成功入场记录。数量来源带来的原额外交付也纳入；失败请求、旧同名随从、其他来源和后来同名物不纳入。该纯连接器由苔缚术原法力奖励共同使用，原两请求默认保持。

支付前保存当前接受上下文、完整接收 ID 和下一笔实际残骸支出及资源操作身份。`FinishCorpseSummons` 核对原完整历史前缀、确切下一笔金额/余额、来源/卡面/操作身份，后来的退款或独立支出不能替换原支付。通过原成功召唤驻留守卫授予关键词：同驻留转控/变形跟随，死亡/离场再入场不取得旧奖励。组内授予仍使用公共关键词生命周期及原通知检查点，未签名材料只证明内部一致性。

当前本地政策在没有成功交付但余额足够时仍扣固定阈值；满场、额外交付、死亡反应后支付及组通知的实际国服语义待 M6，不以内部测试充当官方证明。

## 先扣除、按实际数目复活

亡者大军上限五，白骨卫士指挥官战吼上限六。原接受窗口按实际规则的战场容量与全部物理占位确定可用上限，再由既有 `SpendUpToResource` 冻结实际扣除量。资源反应及其选择完成后，按原实际单位数请求指定固定随从，不在回调中重新读余额。

这里的“复活残骸”是数值资源换取固定新随从，不查询或选取原死亡随从，也不调用死亡历史的复活执行器。

后来的退款不会增加召唤请求，后来的填场可导致交付失败但不重写或退回原支出；数量来源额外交付不额外消耗残骸。满场接受零上限和零支出，不产生虚假随从。此处空位上限、手动可用性和支出/反应/召唤窗口为明确本地政策，仍需对应国服证据校准。

接受时保存实际 `board_limit` 和接受场面，在完整游戏恢复时与原 `Ruleset.max_board` 核对；不能通过改写保存的容量重算支付。有限帧载荷同时校验原来源、完整召唤组、原支出身份和接受前缀，复用原选择恢复、克隆、回放及事务回滚。没有新 GameState 字段；core366/schema291 拒绝旧1～290。

## 固定衍生物和信息

饥饿的幼龙 `CATA_465t` 为5费5/4，同时是龙、亡灵；凶恶僵尸 `RLK_118t3` 为2费2/2嘲讽。复活的步兵 `RLK_061t` 为1费1/3嘲讽，复活的食尸鬼 `RLK_008t` 为2费2/2突袭，后二者原生 `corpse_value=0`，沉默、回手重置和再次入场不把它改成会留下残骸的随从。

[完整原始包](../data/cards/corpse-summon-effects-v1.json)保留四根及四种完整固定依赖。[官网全文及属性对比](../outputs/card-integration-20261014/k71-official-face-01/comparison.json)包括实际 HTTP200 观察、幼龙双种族和直接 child 关系；其他固定 token 按完整原行的 related DBF 和精确卡面确认，不按卡牌ID前缀猜测。旧非核心指挥官卡库页的 Related Cards 指向不同的复活的新郎，不能覆盖固定37核心原行明确的步兵 DBF78570。历史[25.2.2官方调整](https://hearthstone.blizzard.com/en-us/news/23892228)也支持1/3步兵更新，但不替代 CN37 时序校准。

玩家仍只接收原公共资源账户、可见入场和关键词、原白名单日志；原接受上下文、完整交付 ID、资源来源材料、帧及随机状态不投影。内部接入不认证完整标准合法池、构筑热修、国服精确时序或所有可达内容，完整目标保持。
