# 当前牌库数量条件契约

公共声明为 `DeckCountCondition(card_count, comparison, scope='current')`，由现有 `CheckDeckCondition` 执行分支。实际验收与下一项只在 [项目状态](project-status.md) 和 [机制清单](mechanism-backlog.md) 维护。

```python
CheckDeckCondition(
    player_id,
    DeckCountCondition(25, 'at_least'),
    (Draw(player_id),),
)
```

`card_count` 必须是非负的严格整数；布尔、浮点和字符串均拒绝。`comparison` 仅允许 `at_most`（≤）与 `at_least`（≥），两个比较都包含等号。`scope` 仅允许 `current`，不隐式提供起始套牌或其他区域的数量条件。

求值读取指定玩家当前 `DECK` 列表的长度。每个物理槽位计数一次，包括重复牌和所有牌型；手牌、战场、墓地与移出游戏的实体不计入。卡面身份、费用和职业等元信息不影响数量。不缓存计数、不增加玩家资源或历史计数器；后续抽牌、洗入和移除会改变下一次求值。

原 `DeckSizeRule` 约束构筑时容量，`original_deck` 保存构筑原事实。它们不代替当前剩余牌数。Scenario 可以查询当前数量，无须构筑开局证明；起始事实条件的原守卫继续生效。

这是纯结构查询，宿主须提供合法状态，查询本身无需访问定义元信息。正常 Game 操作和存档恢复仍完整验证实体与定义，未知卡牌不能因此进入合法原生状态。查询不产生事件、改变随机数或记录出牌。

未执行的条件在原解释器实际执行位置读取局面；已经选定的分支在等待选择后沿原序列继续，即使牌数已经跨过阈值，也不重新选分支。原支付、历史、事务回滚、选择恢复和回放均复用公共解释器。新条件载荷恰有 `card_count/comparison/scope` 三字段，`CheckDeckCondition` 原四字段保持；额外字段、无效值与未知玩家严格拒绝。

玩家可以看到既有公开 `deck_count`，不能得到私有条件载荷、完整牌库卡面、全知帧或快照。完整状态只供宿主与内部验证使用。

[完整本地 raw 依据](../data/support/current-deck-count-basics.json) 中，JAIL_456 的战吼要求至少 25 张后普通抽一张；必要完整实验适配仅在测试注册表。BAR_916 的至多 10 张条件使用同一数量语义，但其完整目标、吸血及接受窗口仍须独立界定，未作可执行适配。持续费用与持续攻击属性不由这个分支条件自动提供。

本契约是本地实现政策。国服的精确补丁、合法来源池、求值窗口与完整卡牌来源仍需校准；不能据此宣称正式卡池或整族完成。
