# 实际治疗历史与纯查询

治疗量直接复用原 `HealthResult` 的 `healed`，不从请求量、净生命变化、英雄变化次数或余额推算。原治疗准备、转换、数值、吸血、事件、反应与结果续接仍由同一结算器执行。

## 持久事实与接受窗口

`healing_history.py` 只登记原始流或最终流为 `HEALING` 的已结算包。每条冻结 `HealingRecord(id, action, result)` 保存原结果的完整有序负载；`health_result` 属性沿原严格解析器还原结果。没有另一套伤害/治疗数值模型。

零恢复、满血、被规则阻止、治疗转伤害与伤害转治疗均保留原结果；普通伤害、增加生命上限、属性替换、护甲、失效目标略过不凭空生成治疗行。实际量只取 `healed`，治疗转伤害实际量为零。吸血的原辅助治疗包各自登记一次，不重复把原伤害量当作恢复量。

原整批数值和吸血结算完成后，在首个原事件捕获前提交整批历史。首个原 `healed` / `health_resolved` 监听因此看到完整数值批次；没有新增事件或死亡检查点。标识使用原 `batch_id` 与 `packet_index`，不预测事件位置。

`GameState` 增加 `next_healing_id` 和 `healing_history`。记录 ID 连续、游标与完整数量一致，原回合/动作及包身份单调；来源/目标保留原卡面、控制者和物理身份，后续变形、转控、死亡或移区不重写已接受结果。完整当前边界还与有效原结算事件逐条对齐。真正的回溯沿原有效事件退役政策恢复历史；保留结果沿原实际结算继续登记。异常事务恢复历史与数值，失败选择恢复该选择前的已提交边界。

## 公共只读接口

```python
healing_records(state, *, source_player=None, target_player=None,
                target_kind=None, turn=None, before_id=None)
restored_health(state, player_id, *, turn=None)
hero_was_healed(state, player_id, *, turn)
```

`healing_records` 返回完整冻结行的元组，可按原来源玩家、原目标玩家、原角色类型、全局回合和记录前缀筛选。`before_id` 为排他上界。类型和玩家参数严格检查；目标类型只接受英雄/随从。

`restored_health` 累计指定来源玩家实际恢复的单位，可恢复任意角色，包括对手角色。`hero_was_healed` 查询指定玩家英雄在指定全局回合是否实际恢复过正量，不要求治疗来源也是该玩家。两者的对象和计量单位不同，不能互相代替。

无来源的成功治疗仍保存原行，目标英雄查询可以使用；按来源玩家统计正量时明确报 `UnsupportedDefinitionError`，不会猜测归属或静默丢失数量。回合、目标与前缀筛选先界定本次查询范围，范围外未知来源不阻塞查询；无来源零量不产生玩家恢复信用。

这些接口供规则行为使用宿主状态，不能把全知状态交给玩家。玩家观察、命令和回放公共接口布局保持；私有历史、结算结果、规则实例和待选帧不进入玩家日志。

## 必要来源与保存边界

[完整冻结来源](../data/support/actual-healing-history-basics.json)保存 `DAL_799` 晶角雄鹿完整原行与 PIN。仅隔离实验注册表定义完整 5 费 4/4 德鲁伊史诗野兽、突袭和原战吼：累计实际恢复至少 5 点时返回已有 `CopyMinion(source_id, player_id)`，容量与实体生命周期沿原通道执行。没有扩充正式生成池或将其当作最新标准/狂野正式适配。

原序列化和 `FrameCodec` 使用同一完整负载，包括已存在的生命下限计划及分段伤害链接；不截断为单独可变总数。引入时为 `prototype-v229` / `core-effects-v223` / schema212，旧1～211需原引擎。严格解析、摘要及原事件对齐不提供未签名存档的外部来源真实性认证。

来源控制者信用、对手目标信用、转换/吸血归属、整批可见窗及晶角雄鹿精确战吼窗为明确本地政策，仍待国服校准。其他累计历史条件和费用消费者按独立真实需求补充，不穷举组合。实际验收与下一项只在[项目状态](project-status.md)和[机制清单](mechanism-backlog.md)维护。
