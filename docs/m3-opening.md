## 1. 构筑数据与执行能力分开

`CardMetadata` 保存可收藏性、职业集合、稀有度、构筑身份组、单卡数量例外、符文需求和种族。`None` 表示未知，不能当作中立、普通牌或无限制。法术派系继续使用既有 `CardDefinition.spell_school`。

一个卡牌定义可以属于多个职业，中立牌单独使用 `CardClass.NEUTRAL`。双职业牌作为一个定义、任一匹配职业可用的模型有官方资料依据；这不自动确认具体卡在当前模式是否合法。[通灵学园官方介绍](https://hearthstone.blizzard.com/en-gb/blog/23453343/)

`DeckSpec` 保存初始英雄、初始技能、职业、实际卡牌 ID 列表及符文分配。英雄和技能必须有可执行定义及匹配职业；初始技能须匹配英雄的 `initial_hero_power`。默认英雄不能作为普通卡组条目；从手牌打出英雄卡仍属 M4。

`DeckPolicy` 是独立版本化输入，包含策略 ID、目标 ID、模式、允许卡列表、禁用列表、卡组大小、普通/传说卡数量上限和符文槽数。默认采用 30 张、普通同身份最多 2 张、传说最多 1 张、死亡骑士 3 个符文槽。别名版本用 `deck_identity` 合并计数，不用显示名称猜测；单张显式 `max_copies` 可表示数量例外。

`validate_deck` 返回带错误码的 `DeckValidation`，分别报告数量、职业、符文、模式合法性、缺失元数据和缺失可执行定义。同一张牌可能有多个问题。它不会截断卡组、删除未实现牌或把缺少定义的牌当作白板。`Game.from_decks` 在分配对局状态前要求双方校验通过。

死亡骑士的分配总数必须等于策略的槽数；每张牌逐项要求不超过对应鲜血/冰霜/邪恶分配。相同需求不会因放入两张而相加。缺少已核查符文元数据的死亡骑士牌明确拒绝；其他职业不能分配符文。三种符文、三个分配槽及符文决定可加入牌的设计有官方依据。[死亡骑士官方介绍](https://hearthstone.blizzard.com/en-us/news/23852696)

### 模式与证据边界

当前示例策略 `representative-constructed-v1` 使用 `experimental` 模式，只表示通过了指定样本池的构筑约束。`standard` / `wild` 要求调用方提供标为完整的版本池；`pool_complete=True` 是对调用方数据的要求，不是引擎自动核实完整性的证书。M0 必须另外审计地区、轮换、禁限和完整池，不能把可执行代表卡列表复制为正式合法池。

原M3-02批次没有包含全部特殊构筑规则。现有独立容量、游客和侧板基础已接入，具体有限范围见[项目状态](project-status.md)及各契约；完整条件/来源、卡组代码导入和正式模式池仍未闭环，不据常规校验或这些基础宣布全部完成。

## 2. 开局流程

`Game.from_decks(MatchSetup, registry, ...)` 创建普通对局。`MatchSetup` 包含两副卡组、构筑策略、明确实现的硬币 ID、种子和可选固定先手；默认 `first_player=None` 由对局 RNG 选择。测试场景仍可用 `Game.from_scenario` 绕过开局，两种入口明确区分。

官方基础流程是先手 3 张起始手牌、后手 4 张加硬币，双方可替换任意数量，先手第一回合还会抽牌。本原型的普通开局按此构建；详细内部交换及特殊卡顺序仍需目标版本校准。[官方换牌介绍](https://news.blizzard.com/en-us/article/21363040/opening-moves-mulligans)

内核执行顺序：

1. 校验双方卡组与英雄/技能，建立全部独立实体，保存原始卡组 ID 和实体 ID。
2. 决定先手，依玩家编号洗牌，记录 `game_created`，执行 `before_deal` 开局回调。
3. 发先手 3 张、后手 4 张起始牌，保存各自 offered 实体列表。
4. 通过既有 `RequestChoice` / `SelectChoice` 收集双方换牌选择；`ChoicePurpose.MULLIGAN` 与普通效果选择区分。
5. 两方提交后，才按先手、后手顺序统一处理替换。然后给予后手硬币，执行 `after_mulligan` 开局回调。
6. 记录 `game_started`，使先手获得第一个永久法力水晶、发出第一回合事件，并通过公共 `Draw` 抽一张牌。

后手在自己的首回合才按正常回合机制获得第一个水晶并抽牌。硬币是独立新实体，使用已有临时法力效果；不能在换牌时退回硬币。进入第一回合前不接受普通出牌、攻击、技能或结束回合。

## 3. 换牌的实体与随机语义

两个选择目前通过单一 pending 接口依次提交，先收先手、再收后手。这是解释器协议顺序，不宣称真实服务器依次向两个玩家展示界面。第一人提交后不替换其手牌；双方都选完再统一处理，避免第一人的替换结果成为第二人的候选输入。`Game.observe` 与 `player_events` 已提供独立投影，另一方看不到换牌选项和提交内容；完整状态仍是全知的，见 [信息契约](m3-information.md)。开局硬币以公开身份加入后手手牌。

选择 ID 对应具体手牌实体，`option_ids` 使用实体 ID 字符串。可以全部保留、替换部分或全部替换。效果顺序按原手牌顺序规范化，与提交数组的顺序无关。

替换先从尚在牌库中的实体取候选，然后将退回实体放回牌库、把替换牌置入原手牌位置，再洗回退牌。被退回的实体不会被本次替换立刻抽回；同名的另一张副本仍可能出现。全部保留时不额外洗牌；首回合正常抽牌是在退牌洗回之后，因此可以抽到之前退回的实体。该内部算法与位置规则有明确回归，官方精确窗口仍待 M6。

发起始手牌、换牌替换和生成硬币使用专用事件，不作为正常回合 `card_drawn` 事件。真正首回合抽牌复用公共抽牌/疲劳逻辑。`AddToHand` 提供生成牌加入手牌的公共效果：创建独立实体，满手进入墓地并记录烧牌，未知或不支持的牌型明确拒绝。

## 4. 开局回调与扩展

`CardDefinition.opening_hooks` 是一组不可变 `OpeningHook(phase, behavior_id)`。当前阶段是 `before_deal` 与 `after_mulligan`；回调解析原始卡组定义，按先手优先、原始卡组实体顺序调度，每张原始牌对应一次。回调实际执行时获取新状态，后续效果仍经过公共死亡、光环、触发与选择检查点。

`PlayerState.deck_class`、`runes` 和 `original_deck` 保存构筑起点，不随抽牌、洗牌、生成牌而改写；`deck_class` 不是当前英雄职业的替代品。`OpeningState.original_entities` 保留初始实体身份，后续变形不改变这份起点记录。

回调可以发出普通效果或进一步等待选择，帧保存阶段及原结算预算。没有 Python 阻塞输入。开局回调异常或预算耗尽按当前事务边界回滚；开局致命效果直接终局，不强行继续抽牌。

这些阶段是原型公共扩展点；任务保证起手、吉恩/巴库、雷纳索尔等特殊起手/构筑/开局卡并未因此自动实现。不能仅添加标签或挂一个空回调来宣称支持。多个开局能力间的正式排序仍须校准。

## 5. 快照与兼容

该历史批次snapshot schema166同时保存最终起始手牌和 `generation_context` 目标/模式、`match_setup`、完整策略输入、玩家构筑起点、`OpeningState` 和已有结算帧。恢复时重新验证设置，检查原始卡组、实体、换牌阶段、选项和当前 pending 的一致性。普通场景的 `match_setup` / `opening` 均为空。

工厂内的开局结算可以在 action 0 挂起，随后玩家选择分别进入动作历史；根预算持续累计。动作 0 的帧只允许用于有正式开局设置的对局。对局 origin 可为第一次换牌或更早开局效果的等待快照，回放从此重算后续操作；同种子重新建局也经过一致性测试。

更早原批次 schema 74 明确拒绝旧 schema 1～73，外层 replay schema 仍为 1。该更早批次内容已包含构筑元数据、两个初始英雄和实验发现池，代表包为 `representative-m5-v38`；所有恢复仍需匹配规则、效果签名及注册表指纹。

## 6. 运行与验收

[卡组设置](../examples/matches/constructed.json) 使用吉安娜/火焰冲击与加尔鲁什/全副武装，两副 30 张实验卡组均经过普通构筑约束校验。新冻结英雄记录 `HERO_08` / `HERO_01` 与既有代表记录一起，该原批次合计 269 条真实样本，均保持 partial / internally_tested。

```powershell
# 只创建对局，停在首次换牌，输出选项并保存等待快照
python -m hs_sim match examples/matches/constructed.json --snapshot-out outputs/opening-pending.json

# 双方换牌、切换至后手并打出硬币
python -m hs_sim match examples/matches/constructed.json --actions examples/actions/constructed.json --replay-out outputs/constructed-replay.json
python -m hs_sim replay outputs/constructed-replay.json --card-set representative

# 从开局等待快照恢复，用固定演示策略运行到终局并重算回放
python -m examples.play_constructed
python -m hs_sim replay outputs/constructed-complete-replay.json --card-set representative
```
