# 真实发现的原选项配方

源生之石（TLC_460t）需要使用本次发现的其余选项。可见的 `ChoiceItem` 和 `CardPreview` 只能说明菜单与预览数值，不能反推出完整附魔、原物理引用、复制方式或后续生产者。`OriginalDiscoveryOffer` 保存共享选择入口实际收到的完整有序 `ChoiceOption`、原 `PendingChoice` 和原回调身份；未来消费者必须使用这些原配方，不能从后来同名手牌、诊断搜索或虚构的出牌历史找对象。此契约只描述配方保存，实际进度与下一项仍仅在原两份台账维护。

入口先沿原抽样、场上发现和地图绑定生成真实菜单，再在所有手动/自动选择分派之前接受同一份原工作。`card_discovery_offer_accepted` 是不捕获游戏触发的私有一致性记录，不增加效果指令、随机或游戏检查点。未选择时不产生 `CardDiscoveryRecord` 或发现后通知。选择提交时，原不可变记录新增 `original_offer`，用受宿主允许列表限制的 `FrameCodec` 保存该完整 typed 配方；字段只在构造时写入，后续交付不修改原记录。费用前缀因此自然冻结同一份原选项，不能在后来补写材料。

普通池分支保留完整候选、原查询、逐项黑暗之赐配对及原未绑定状态；物理分支保留原 `CardReference` 与复制/移动请求；地图与选择死亡记录保留自己的真实生产者链接。core462 的配方引用本身不等于每张物理牌的属性快照；core463 随后增加菜单原窗口的完整物理材料，见[原卡材料契约](m3-offered-card-materials.md)。原引用的实际交付窗口仍由对应生产者校验，不能用预览冒充完整副本。`offer_for_result` 只读取完整匹配的原提交记录，`unselected_options` 按原顺序排除实际选中的 ID，不重新抽样或合并同名实体。

恢复检查完整提交、原接受事件与原配方一致，原等待帧及回调须与接受时相同；即使重新计算存档哈希和提交发布收据，也不能单独改变原未选分支。异常回滚保留原开放菜单，真正回溯退役旧接受事件与记录，重试使用新的实际选择身份。私有接受事件、完整工作与卡牌发现历史不进入玩家投影。该检查只证明当前存档内部一致性，不提供未签名存档的外部来源认证。

本增量使用 core462/schema379，旧1～378存档必须使用原引擎；内容v259、观察93、命令12、replay1保持，无新增卡定义、实体/玩家/游戏状态字段或生产效果，仅新增一个不可变记录字段及一个 codec payload。原实际交付与 `card_discovered` 时序继续沿[既有交付契约](m3-discovery-delivery.md)。

本配方增量本身没有注册TLC_460/TLC_460t。后续core464把原未选项及冻结材料作为独立真实来源连接既有整卡解释器，原物理/附魔、顺序、嵌套和武器身份见[执行契约](m3-original-offer-execution.md)；不能伪造历史提交、只执行法术，或把保存配方宣称为整卡已经完成。实际整卡验收仅以原两份台账为准，M0正式池和M6国服时序保持独立。
