# M3：每名玩家独立手牌容量

本页维护实现与扩展契约，执行结果和下一项仅见[项目状态](project-status.md)与[机制清单](mechanism-backlog.md)。完整正式池及国服时序按[长期计划](roadmap.md)保留。

## 真实需求

瓦迪瑞斯·邪噬 `DRG_208` 的完整本地原始记录要求提高本人手牌上限至 12，再抽四张；扩音机 `ETC_087` 的完整记录要求将本人法力和手牌上限设为 11。只改全局 `Ruleset.max_hand` 会同时改变对手容量，无法表达这两项独立规则。

[官方 16.2 更新说明（2020-01-21）](https://hearthstone.blizzard.com/en-us/news/23239995)说明补满手牌效果必须遵守瓦迪瑞斯修改后的手牌上限。该公告及本地完整记录证明动态本人容量的需求，不证明当前正式合法池或全部国服细节。必要代表只在独立实验夹具注册完整瓦迪瑞斯，原始记录和指纹见[实验支持包](../data/support/per-player-hand-capacity-basics.json)；扩音机只作原始需求证据，没有在本项提前接入其完整卡牌或组合。

## 状态、查询与效果

从 [hand_capacity.py](../hs_sim/engine/hand_capacity.py) 导入 `hand_capacity` 和 `SetHandCapacity`。

| 入口 | 契约 |
| --- | --- |
| `PlayerState.hand_cap` | `None` 表示采用规则包的初始默认值；显式值为严格正整数的玩家容量覆盖 |
| `PlayerSetup.hand_cap` | 场景可分别设置双方容量；原未指定场景保持默认，起始手牌必须容纳于各自容量 |
| `hand_capacity(player, rules)` | 无副作用纯查询，读取本人覆盖或 `rules.max_hand`；没有另一份可用容量缓存 |
| `SetHandCapacity(player_id, amount, mode='set')` | 将本人容量设为严格正整数；不自动抽牌、移动、弃牌、烧掉已持有材料或消费 RNG |
| `mode='raise'` | 取当前有效容量和请求量的较大值；对应“提高至”政策，不降低更高的已有上限 |
| 实际数值变化 | 发原公共事件管线中的 `hand_capacity_changed`，记录玩家、差额、前后容量和模式 |

永久水晶上限仍由 [法力账户](m2-resources.md) 管理。手牌容量不绑定当前英雄、来源随从或附件；来源离场、沉默、变形及英雄替换不会撤销已写入的玩家容量，回合交接也不清除。实体复制或转控不复制玩家账户，特殊来源的撤销或期限需求待真实卡需要时另行判断。

## 原入区路径与补满

18 个原入区、整组容量与补满检查共用查询：普通抽牌及抽到时施放、生成/复制/物理移动、回手、弃牌材料取回、手牌衍生物、自动法术衍生物、发掘奖励、裂变片段、临时卡、开局发牌/硬币、起始手牌与临时手牌/牌库手牌的恢复、虚空取牌，以及 `DrawToHandLimit`。各原模块保留既有物理材料、获取身份、重置、烧牌、候选和触发语义；没有新交付解释器。

每次实际交付查询当前收件方容量，不按来源控制者或旧全局默认值判断。入区后反应改变容量，后续抽牌继续读取新值。`DrawToHandLimit` 保留原请求窗口计算抽取量的政策，后续每张是否入手仍由原抽牌入口实时判断；不是循环到永远补满。整组临时手牌恢复等入口保持各自原整组资格政策，只改容量依据，不提前扩展不同机制之间的恢复组合。

`construction.py` 的正常开局默认容量前提和玩家观察顶层默认 `limits.max_hand` 保留；它们没有代替本人有效容量。正常开局的实际发牌与硬币交付已采用每名玩家查询。

## 已持有手牌与边界政策

容量约束新材料的入区。设置较低容量不主动删除已持有材料；手牌暂时超过容量时，后续入区仍按原烧牌政策拒绝，直到实际空位足够。稳定校验检查覆盖值和物理区域一致性；未扩容的默认状态仍拒绝超过默认容量的手牌，显式降低容量后的已持有超量状态不自行删牌；场景初始建组仍明确拒绝超容量输入。

该降低容量/超量保留政策及“提高至”的准确解释是明确内部契约，待国服校准。这里只表达设置容量自身的行为，没有以各类关键词或来源组合扩大验收范围，也不把支持扩容和补满当作全部手牌特殊规则完成。

## 选择、付款证明与玩家信息

容量覆盖进入原完整状态、选择帧、付款前后证明、克隆和逐动作回放。变化前/后等待、付款后等待、抽牌中暂停和失败回滚均复用原解释器。卡牌不得直接写玩家状态或在闭包中另存容量；未知模式/无效玩家/非正整数明确拒绝。

双方玩家对象公开有效 `hand_cap`；顶层 `limits.max_hand` 保持规则默认值，消费者应读取具体收件方玩家字段。容量可见不意味着对手手牌、牌库顺序、内部付款状态或 RNG 可见。原玩家目标 DTO 增加严格正整数容量字段；付费接受时绑定完整原观察，后续容量改变不改写已接受的目标输入。
