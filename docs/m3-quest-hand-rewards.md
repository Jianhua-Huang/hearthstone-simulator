# 任务手牌奖励的容量等待

这是有限公共交付契约，实际进展、验证与下一项仍只在[项目状态](project-status.md)和[机制清单](mechanism-backlog.md)登记。没有认证完整国服时序或所有定制奖励来源。

[开发者原评论](https://www.reddit.com/r/hearthstone/comments/1lel19h/comment/myk6eia/)说明：完成任务时手牌已满，手牌奖励不烧毁，完成状态保留，之后有空位时交付；并明确包含旧安戈洛和暴风城任务。对整个支线任务家族的答复仍属暂定，不能据此认证所有来源。

## 接受与交付

只有真实 `quest_stage_completed` 所调用的声明奖励行为，才将直接 `AddToHand` 及其直接选择选项中的同类指令包装为 `GiveQuestHandReward`。普通造牌、抽牌及非手牌奖励维持原入口。通过后续发现回调或定制建造器产出的奖励，接卡时必须显式携带原完成原因；本契约没有自动覆盖任意回调后代。

接受时保存原任务分配事实、实例、阶段、完整完成事件及奖励配方。先核定义与创建材料，未知内容立即报错，不等腾出空位才失败。满手时不分配实体、不生成烧牌事件、不消耗随机数；没有已审查期限政策的临时创建奖励明确拒绝延迟。原任务阶段的后续完成流程保持，等待义务独立于原实体后来所在区域。

有空位时仍由公共 `create_hand_card` 创建真实新牌，按返回的实际实体记录交付，再发布普通创建及入手通知。已有费用和其他创建授予沿原配方安装；不按卡名寻找新对象，不伪造抽牌。实际记录先提交，后续入手反应可正常选择、保存或失败回滚。

公共效果检查点只排一个内部补发标记，原已捕获反应保持顺序；待交付组按原接受顺序处理、执行时重核收件方实际容量。当前高弗雷返回在可交付任务奖励之后执行，不消耗被任务奖励占用空位的抽选随机数。这是有限内部排序政策，仍须国服校准，不代表已穷尽所有等待来源。

## 保存与边界

`GameState.quest_hand_rewards` 保存原接受及实际交付记录，严格解析原配方和事件；普通玩家投影不提供私有等待列表、来源材料或内部收据。恢复验证实际完成、接受/交付收据、队列及真实奖励选择，拒绝裁义务、换配方、借完成事件或注入内部标记。继续复用原有效事件视图、回放、异常回滚及终局前缀。

精确检查点、多个等待奖励的排序、任务区域占位及通知、定制发现/拼接奖励、生成与取得时材料、支线任务完整范围和高弗雷交互均保留待校准边界。相关实现见[公共交付模块](../hs_sim/engine/quest_hand_rewards.py)和[必要代表测试](../tests/test_quest_hand_rewards.py)。
