# 对局中牌库容量与原交付结果

运行中的牌库容量由`engine/deck_capacity.py`统一为99。依据是[官方团队的原始答复](https://www.reddit.com/r/hearthstone/comments/1tux9zu/comment/opd6wu2/)，该答复只证明上限从60改为99，不证明国服37.0的热修集合、溢出触发或精确窗口。正式构筑的起始牌数另由构筑规则决定；实验Scenario可以包含更大的原输入，但运行时不能继续扩容，也不会删除原输入以伪造合法牌库。

生成和复制先核对完整定义、材料和费用/授予资格，再检查实际容量。满容量不分配新实体、不安装附件、不随机定位，也不发布成功入库或成功洗牌；未知内容仍明确拒绝。有限原请求留下私有`deck_entry_failed`结果。计数式`ShuffleGeneratedCopies`仍只物化可用位置，不为巨大原请求展开逐张失败实体或事件，原数量保留在既有语义洗牌声明。

原存储卡的移牌失败与生成失败有不同结果。HAND或另一牌库的原实体交付到满牌库时，原实体进入收件方墓地，保留原owner，使用同一普通存储销毁通知和`deck_overflow`原分配收据；不是弃牌或战场死亡。原场上随从不能洗入时，仍在原控制者场上被标记消灭，再由普通死亡检查点执行亡语、残骸等。已经死亡的随从/武器不能重新入库时留在原墓地，不重置、增加成长或再次销毁。**这些溢出结果、可见性和触发顺序为明确本地政策，仍待M6国服校准；官方99张答复没有证明它们。**

同一张原牌在本牌库内重新定位不占新位置，满容量仍允许。普通AddToDeck、MoveCard、CopyCard、ShuffleIntoDeck、原死亡实体及武器回库和临时牌库手牌归还共用容量查询。Resolution的直接创建/移动入口另有守卫，拒绝绕过容量处理的运行时写入；初始Scenario材料化不冒充对局入库效果。普通随机定位和成功语义洗牌执行器保持。

发现记录保留完整原选择和配方。未能生成到牌库的首要结果为`DiscoveryCompletion.recipient=None`，原同步交付窗口必须存在对应玩家、来源和卡面的真实满容量失败；不能借同名实体替代。亢祖的对手牌库顶和从对手牌库复制后授予甜美梦境共用这个结果。已失效的原物理引用仍沿既有明确跳过语义。

传奇商贩和跳脸惊吓的未选项仍按完整原槽顺序结算；每个原槽保留成功分配或空失败结果，并与同一同步窗口中的实际插入/失败事件核对。语义shuffle的declared_count仍为全部原余项，只有成功入库的实体成为成员；全失败不造shuffle。选中的甜美梦境已满容量时也保留原发现、无实体的交付证明和未选项义务。原卡面、赐福、费用和关键边界不因容量裁掉。

临时借用牌在真实归还窗口按原有序物理身份尝试入库。TemporaryDeckHandReplacement保留全部`removed`尝试，新增`deck_burned`记录未入库的后缀；成功前缀、原完整牌库及随机前后状态共同验证实际洗牌。每份失败另绑定原temporary_hand_id及真实完成窗口，并与原失败后缀逐项核对；即使同步修改组记录与完成收据，也不能遗漏仍在原时间线中的失败或借其他组冒充。全失败不洗牌或消耗随机；原私藏手牌恢复、满手烧毁及新获得卡保留仍沿旧机制。完整原完成记录先于反应发布，等待、回滚、恢复、克隆和回放不重新分配这些结果。

失败事件、原分配及余项/临时归还证明只进入内部状态或事件，不进入玩家DTO。恢复检查证明内部时间线和实体一致性，不认证未签名存档的外部来源。实际验证、当前版本、差异和下一项只在原两份台账登记；正式池、国服校准及全部实际可达内容的门槛保持。
