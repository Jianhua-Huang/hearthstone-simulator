# 标准传送门的自动施法来源与回溯收据

本页维护表达与保存契约；实际执行、证据和下一项仅在[项目状态](project-status.md)及[机制清单](mechanism-backlog.md)。[原生来源契约](m3-static-provider-cards.md)中的旧交付点必须先按真实卡牌和标准可达关系核对，静态调用点不能直接当作缺失机制分母。

## 真实依赖与已有入口

金萼幼龙的战吼/亡语灌注圣骑士技能，巨龙的祝福将两张翡翠传送门洗入牌库，传送门由真实抽取流程自动施法。传送门主体给已有`SummonFromPool`显式传入`SummonCause.capture(context)`，使选择、当前数量来源、支付与来源所属各自沿原管线处理。造成召唤的是这张传送门的实际自动施法，外层抽牌法术不代替它；对手的卡德加不向该施法者提供数量。

入口在没有数量来源时也保存完整归因及原候选依据，不以当时有没有卡德加丢弃来源。第一次接受时选定模板与完整次数，额外实体共用模板；源后来死亡不取消已接受的余量，场位仍逐次检查。玩家等待、失败回滚、clone和回放复用原解释器，不另建召唤执行器。

旧`GenerateFromPool`、`SummonFromCandidates`和`SummonFromPool`已有带`cause`的完整分支，无来源分支保留明确拒绝。Adapt植物配方未由当前生产工厂安装；旧星港/升空和两个替代目标奥秘不在当前标准候选根中。本次审计没有证明它们绝不可能被标准卡触达；后续由实际标准入口或可达依赖证明需要后再接通，不提前创造新的替代目标数量政策。完整可达图与正式合法池仍是目标义务。

## 回溯前后的物理施法

回溯重试可保留旧事件而恢复当前施法历史。两次自动施法的数字ID可能相同，物理来源却不同；历史收据不能只凭数字去匹配今天的`cast_history`。

当前局面与待选状态继续使用完整当前施法记录严格校验。历史召唤接受/结束收据另外按原事件顺序索引已有`spell_cast_accepted`事实，绑定施法号、物理来源和受益玩家，并检查原接受事件不晚于召唤接受窗、动作不来自未来。原来源分配、完整接受/结束一致性、选择与RNG证明，以及旧根只能因后续真实回溯离开当前状态的约束保持。缺失原接受事实、借用外层抽牌施法、换物理来源或换玩家均拒绝。

没有新持久字段或事件格式；历史索引仅在校验时建立。它证明现有日志与收据的内部关系，不提供未签名存档的外部来源认证，也不把已被回溯删除的完整旧施法记录重新构造成官方证据。

## 证据与版本边界

`python -B -X utf8 -m examples.card_khadgar_portals`使用真实定义及玩家操作完成幼龙、技能、洗入和抽取链，各稳定位置独立恢复、clone与回放。所用原龙池仍明确是五成员实验池，不能据此认证正式标准龙池或完整传送门支持。正式池的所有合格卡及未知内容的明确错误、Core身份、补丁热修、国服精确窗口和M6仍需各自完成。

本变更使用现有状态布局和玩家协议；格式由`SNAPSHOT_SCHEMA_VERSION`声明，行为版本单独更新。布局相同不代表旧规则快照可自动兼容。实验场景的混合职业、显式法力和受限池仅用于内部验证。
