# 实际成功复生的历史与查询

这是`CAP_806`雷斯·范盖斯特真实卡面要求的必要历史能力，来源见[固定原行及双语主面](../outputs/card-integration-20261014/k165-source-preaudit-01/source-review.json)。实际进度、验收及下一项只在[项目状态](project-status.md)和[机制清单](mechanism-backlog.md)维护；此能力不单独宣称整卡完成。

## 原成功记录中的有限分类

既有`SuccessfulSummonRecord`末尾增加`reborn_death_id: int | None = None`。普通使用、召唤、复制、复活及其他原入场保持`None`；只有实际原复生执行器成功发布的入场才保存原死亡ID。没有新的State/Entity/Player字段、平行复生账本、玩家计数器、Effect或显式payload类型，也不改原死亡、复生与巨型执行器。

原`colossal.announce`的内部reason为`reborn`时，既有`minion_summoned`载荷使用`reborn_from/death_id`，随后发布`minion_reborn`；内部reason不是新增公开事件字段。分类由这一次真实成功发布点提交，先于普通召唤监听者捕获。死亡时有复生、分配过返回请求或之后场上出现1生命随从都不是成功证明，满血保留附魔复生也正常计入。

链接必须指向完整实际BOARD死亡行，原卡面、死亡控制者、原复生关键词、死亡时钟和父子分配/入场顺序必须一致。成功返回的是由原死亡控制者获得的新实体；原尸体的owner可不同，不改变历史中原接收玩家。死亡ID可能因回溯跳号，按原ID连接。后续死亡、变形、移区和转控不重写已有事实；同卡面再次真正复生是另一个发生。

## 纯查询及完整性

`hs_sim.engine.successful_reborns(state, player_id)`返回按原成功顺序排列的冻结记录tuple。它复用原完整成功历史校验，不读宿主诊断日志或当前场面，不按名称/关键词推测来源，不消耗RNG，也不要求已知种族。玩家编号严格拒绝布尔值及非法编号。

原稳定边界继续沿`effective_events`只核当前提交时间线，保留撤销分支的诊断日志。每条复生分类必须与原成功入场的`reborn_from/death_id`一致，且完整分类清单与真实`minion_reborn`事件逐一对应。只删分类、只删入场标记、用普通复制冒充或替换原死亡都会拒绝；不提供未签名存档的来源认证。

新保存对该记录严格要求显式字段，普通发生也必须有`null`。schema370拒旧369及更早，core453保护执行身份；公开观察92、命令12及replay1布局保持。完整死亡链接和私有历史不进入玩家DTO。

## 尚未由本能力闭合的需求

CAP_806仍需冻结原成功复生材料，沿原复活执行器交付，再让那些实际返场者攻击随机敌方随从。现有固定法术召唤攻击profile和逐体复活`on_summon`不能自动证明整组窗口；不能据本次历史能力登记其可执行定义。精确计次、复生/入场窗口与完整国服校准仍保留M6。
