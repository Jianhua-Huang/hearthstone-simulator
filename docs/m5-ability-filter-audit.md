# 13d-02e 前置审计：能力条件与物理候选

本页保留v78时的前置审计；v79已接入下述筛选，当前契约与证据见[公共能力筛选](m5-ability-filters.md)。原审计如下。来源为[固定本地候选](../outputs/m5-13d-02e-filter-candidates.json)，不代表正式池合法性或国服规则验证。

毒鳍龙 `TID_710` 需要给牌库里具有战吼的随从增益；湍流元素特布勒斯 `WORK_013` 涉及手牌、牌库、战场中的其他战吼随从。这说明能力条件不仅用于费用，也需要进入物理对象选择。后者的游客构筑约束应单独登记，不为演示战斗筛选宣称整卡或构筑已支持。

目前 `MinionScope` 和 `zone_candidates` 使用 `PoolQuery` 的印刷元数据条件，`matches_metadata` 没有实体能力上下文。v78 的 `CardAbilityCondition` 可判断当前/印刷身份，但仅已接入费用。`BuffStoredCard.cost` 的筛选决定费用操作是否有效，不是选择增益对象的替代接口，不能先选中非战吼卡再借费用验证跳过。

下一步需要一个显式的筛选上下文契约：实际实体查询能接收当前能力；新建池候选只有基础定义；印刷元数据字段维持原义。不能在无实体路径悄悄把“当前”改成未知、忽略条件，或靠卡文标签推断。应复用已有条件匹配，同时审查所有候选调用者，避免一个 PoolQuery 字段在不同入口被静默忽略。

验收包括：手牌/牌库/战场正反例、同卡不同附件、沉默/变形/升级、来源物理排除、实体捕获后的移动/返回/替换、无目标、批次和随机抽样前的验证、非法配置回滚、隐藏牌日志、挂起恢复及回放。基础生成候选和实体批次的能力查询要明确区分。优先一个必要代表，跨区组合可以先用合成机制，不为数量补牌。

动态战吼授予不能仅因计划写有缺口就先造通用接口。本地石裔指控者 `REV_013` 的“注能后获得战吼”可先检查现有手牌升级是否已能表达；酒馆与冒险文本不进入传统构筑主线。真正需要保留多个声明来源或授予主体的构筑候选，须明确后再扩展能力实例。历史/间接战吼来源仍按13d-03独立推进。
