# M5-13d-03d-01 前置审计：有上限的历史战吼序列

本页记录下一公共依赖，未实现限额序列或沙德沃克适配器。GIL_820中英文字及canonical指纹保留在[既有来源](../outputs/m5-13d-03-source-candidates.json)。它是传统构筑卡，不应混入同名酒馆英雄的技能政策。

2026-09-25核对了官方[11.1更新说明](https://hearthstone.blizzard.com/en-us/blog/21738246)：2018-05-08将沙德沃克重演上限明确设为20次战吼。这说明至少有一个公开的卡牌规则上限，必须和Ruleset.max_resolution_steps工程预算分开。该历史公告没有证明当前国服是否存在后续修订，也没有明确组合主体、选择顺序和嵌套重演如何计数；后者仍需记录政策并校准。

当前`RepeatPlayedBattlecries`可以冻结第一/最后/全部已完成出牌，按历史或随机顺序执行；每次出牌可能携带多份战吼声明。它只有工程步数预检，没有独立规则上限、按声明筛掉自身能力或把组合主体展开后取样的通用入口。直接把引擎预算改为20会误伤其他结算；只取前20次出牌又不等于最多20份战吼主体。

可复用的工程模式已经存在：`spell_history.RecastFromHistory`和`ContinueHistoryCasts`保存冻结候选ID、剩余请求次数和历史上界，分步选择、执行并恢复；`ContinuePoolCasts`也校验剩余次数不超出请求。下一项先检查这种类型化续接能否适用于“出牌ID＋捕获战吼主体”的序列。法术历史的对象是实际施法记录，战吼候选可能是尚未实际激活的出牌声明，不能直接用法术记录或实际激活历史代替。无需另造通用队列，也不能把该工程模式当作沙德沃克取样顺序的官方证据。

## 先明确的契约

- 选择单位是一次出牌还是其中一份捕获主体；同一出牌的多附件顺序以及重复打出同牌是否独立计数。
- 自身排除按捕获出牌卡ID、声明卡ID或行为身份判断，不能仅排除当前play_id后就宣称符合“其他战吼”。
- 限额是先取历史前缀再洗牌，还是在完整候选中随机抽取到限额；没有证据时不能把这两种政策混称随机执行。
- 父序列开始时冻结候选、顺序与限额；之后召唤、变形、回手、转控、发现暂停和新历史不能扩张已接受的序列。
- 无目标、反制历史、未实际激活的提交、组合星舰与嵌套鹦鹉如何计入限额；工程预算耗尽依然报错回滚，不能冒充规则截断或平局。
- 持久化待执行的限定序列及原声明来源，检验恢复后的数量/顺序/归属和篡改；继续使用共享RNG、间接目标/选择和玩家隐私边界。

13d-03d-01应先补公共序列契约和边界验收，再决定必要代表的完整政策。动态主体和连击重复各有独立缺口，不能为了快速接入沙德沃克将普通on_play全部视为战吼。此前R-120～R-123、M0完整池、M6集中校准和M7批量适配保持未完成。
