# M5-06：巨型、附肢与可恢复入场

下文保留普通巨型的历史基础契约。真实有限余量来源的初始入场与后续空位补充见[有限巨型契约](m3-colossal-reserves.md)；普通巨型满场失败不自动补发的政策保持。

当前 `prototype-v75` / `core-effects-v75`、snapshot schema 74、`representative-m5-v38`、`player-view-v44`，玩家命令为 v7。本批建立巨型的公共入场机制及三个主体、十个不同附肢的真实记录。正式完整池及特殊巨型仍未完成；兆示基础在 [M5-07a](m5-herald.md) 接入，其余职业分支待续。

## 主体与附肢独立存在

巨型主体以 `Keyword.COLOSSAL` 和 `CardDefinition.colossal` 声明一组有序 `AppendageSpec(card_id, side)`。每条附肢声明明确卡 ID 和 left/right 落点，允许重复卡 ID；不能把原始 `COLOSSAL=1` 标签误解为“只召唤一条附肢”。附肢本身是独立随从定义和实体。

```python
from hs_sim.engine import AppendageSpec, CardDefinition, CardType, Keyword

body = CardDefinition(
    'example.body', '巨型示例', CardType.MINION, attack=3, health=5,
    keywords=(Keyword.COLOSSAL,),
    colossal=(AppendageSpec('example.left', 'left'),
              AppendageSpec('example.right', 'right')),
)
# 还需注册对应附肢的普通随从定义。
```

注册时拒绝缺失声明、错误类型/落点；冻结时检查全部附肢已实现且是非组合的物理随从。当前不接受递归巨型附肢，也不支持直接授予裸 COLOSSAL 标记。普通附肢可独立召唤、攻击、受伤、死亡、被沉默、复制、回手或转控；它们没有与主体共享生命或强制共同离场的关系。

[官方巨型介绍](https://news.blizzard.com/en-us/article/23784370/voyage-to-the-sunken-city-is-now-live)明确：主体被召唤时，附肢也会出现，即使主体不是从手牌打出。公共处理因此位于 [colossal.py](../hs_sim/engine/colossal.py) 的入场调度，而不是代表卡的战吼中。具体复制、变形、事件窗口等仍是待国服 M6 核实的实现契约。

## 分步结算与容量

当前契约按以下顺序展开：

1. 来源路径先让主体占据一个场位，并安装该路径要求的当前状态、复制信息或复生生命。
2. 建立不可变 `ColossalRecord`，排入逐条 `SummonAppendage` 和 `FinishColossal` 继续步骤。
3. 每条附肢执行时重新检查宿主身份和控制者，并重新检查剩余场位。成功创建的附肢有独立 ID 和召唤事件；随后执行反应及死亡检查，再处理下一条。
4. 完成后发出主体召唤事件；从手牌打出的巨型之后才读取战吼和完成出牌。变形路径保留 transformed 事件，不冒充主体被新召唤。

满场不能打出主体；只有一个空位时允许主体登场，附肢逐条记录失败。部分空位按声明顺序使用；失败项不会在后来自动补发。附肢反应若腾出场位，后续附肢可使用该位置。左侧按声明顺序放在主体前，右侧保留已生成的右侧附肢顺序；全部使用共享场位容量，地标等占位也计算在内。

`ColossalRecord` 保存原主体 ID/卡面/控制者、回合与动作、区域修订/入场顺序、来源种类、复制或复生来源、各项成功实体 ID 或失败空值，以及 attempted/completed/canceled。它是历史与继续步骤的依据，不是将场上实体永远捆绑的父子关系。

主体在展开中离场、易主、换形或被新的同体展开取代时，当前契约取消剩余项，已生成附肢保留。单纯沉默不撤销已经排定的附肢步骤；沉默后的当前状态复制没有可用巨型标记，不新建展开。终局会关闭未完成记录。**R-067** 跟踪展开、反应、主体事件及战吼顺序；**R-068** 跟踪来源取消、复制/变形/沉默和位置边界。

## 统一入口与生命周期

| 来源或操作 | 当前处理 |
| --- | --- |
| PlayCard 从手牌打出 | 原实体登场，正常支付一次；附肢不额外支付也不计为手牌出牌 |
| Summon / 固定候选召唤 / 生成池召唤 | 新建主体并展开；不执行战吼 |
| SummonStoredCard | 以受区域修订保护的 CardReference 从手牌/牌库移动原实体；保留当前属性，不计抽牌/打出 |
| CopyMinion current | 复制主体当前状态，新主体重新生成基础附肢；不复制原附肢的伤害与增益 |
| CopyMinion base | 使用印刷主体重新生成基础附肢，即使原主体已沉默 |
| 复生 | 新的一血主体重新展开；附肢使用自身完整基础生命 |
| Transform 变成巨型 | 保留原实体和行动状态，按新定义展开附肢 |
| 回手后再次打出 | 老附肢保留；主体再次展开一组新实体，仍受当前容量限制 |
| 转控、休眠/唤醒、场景初始摆放 | 不视为新召唤，不重复展开 |
| 主体死亡、变成普通随从或单独回手 | 既有附肢保留其当前状态和控制者 |
| 单独复制或召唤附肢 | 只有该普通随从，不自动补主体 |

`SummonStoredCard` 支持指定新控制者，owner 保持原主人，附肢属于实际召唤方。满场时原手牌/牌库实体不移出、不公开；过期引用不命中新返回或换形的卡。它只处理手牌/牌库物理实体，不能代替未来完整招募筛选、复活池和其他施放来源契约。

奥秘中召唤替代攻击/法术目标的路径也接入同一入场函数；星舰发射使用独立的组合模型，注册表不允许将其模板混作巨型。磁力不传递巨型入场标记。

## 真实代表及公共效果

| 主体与附肢 | 验证点 |
| --- | --- |
| TSC_216 黑水巨鳗、TSC_216t 巨鳗的诱饵 | 左侧附肢、独立回合末触发、迫使敌方随从攻击友方巨鳗、吸血 |
| TSC_639 暴食巨鳗格拉格、TSC_639t/t2/t3 尾巴 | 三条不同 ID 的嘲讽附肢；友方死亡后获得死亡记录的基础属性，不获得临时增益 |
| TID_711 厄祖玛特、TID_711t/t2/t3/t4/t5/t6 触须 | 六条不同 ID、满场；亡语按当前存活友方触须数量安排连续随机消灭，每次重新查询敌方战场 |

基础属性来自冻结本地源，十三条记录各有独立哈希。外观相似、同名的附肢仍保留真实 ID，不合并成一个衍生物 ID。精确多主体、沉默/转控及随机选择窗口仍待校准，均标 partial / internally_tested。

`RandomForceAttack` 是公共效果：对当前仍有效的敌对随从配对作可回放的随机选择，再复用已有 ForceAttack/战斗窗口；卡牌行为不直接扣血或自行操纵攻击次数。原型目前对多个巨鳗在候选对中均匀抽样，相关正式目标选择仍由 R-068 跟踪。

## 恢复、隐私与验证

schema 74 拒绝旧 1～71。快照保存完整展开历史，待选择帧保存余下附肢、主体完成和战吼继续步骤。恢复验证历史类型、序号、实体/原所有者、顺序、复制/死亡来源，以及每项未完成展开必须有正确的后续步骤。伪造摘要不能绕过这些结构检查；这不是任意自洽历史的服务端真实性认证。

玩家观察仅显示已知卡面当前有效的 `colossal_appendages` 卡 ID/落点。对手手牌继续受原信息隔离限制，不显示内部展开记录和实体分配信息。无需新增玩家动作种类，现有 PlayCard 和固定座位入口可用。

52 项专项覆盖各来源、容量、独立生命周期、分步反应、挂起恢复、全局终局/回滚、真实行为、存档篡改与玩家隐私。`examples.colossal_appendages` 用五次玩家命令打出格拉格和黑水巨鳗，诱饵触发战斗后再用火球消灭另一条尾巴，验证主体的基础属性增长、中途恢复及完整回放。这是混合职业机制场景，不是正式合法卡组。

```powershell
python -m unittest discover -s tests -p test_m5_colossal.py -q
python -m examples.colossal_appendages
python -m hs_sim replay outputs/colossal-replay.json --card-set representative
```
