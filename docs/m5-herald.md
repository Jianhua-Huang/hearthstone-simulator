## 规则依据与实现边界

[国服机制公告](https://hs.blizzard.cn/news/24245219/index.html)说明兆示会召唤职业士兵，两次、四次提升士兵及对应附肢的强度，并增加死亡之翼的灾变数量；[国服上线公告](https://hs.blizzard.cn/news/24250357/index.html)确认机制已经上线。冻结本地数据中的 CATA_158 是亡语兆示、CATA_492 是地标主动效果、CATA_530 是法术效果，因此不能将文章中的简述直接实现为“每打出一张 HERALD 标记卡就加一”。真实效果由手写行为调用公共效果。

正式公告没有穷尽召唤与计数的精确先后，也不能证明当前热修下的全部特殊交互。本批明确记录以下内部契约，尚未获得国服逐事件校准：

- **R-069：阈值与事件窗口。** 每次兆示先按已有完成次数生成士兵，再提交此次计数和历史，之后派发公开事件及召唤反应。因此第 1/2 次为基础士兵，第 3/4 次为两倍，第 5 次以后为四倍；完成第 2/4 次后的其他附肢召唤立即读取新等级。事件反应看到已提交的计数。召唤失败也计数；原有场上士兵不自动升级。
- **R-070：形态与职业边界。** 使用当前英雄职业选择士兵，英雄替换保留本局计数；沉默移除强化属性与能力，当前复制保留捕获等级，基础复制/回手重打/复生按新控制者进度重新建立。非兆示职业以及尚未实现的职业分支目前明确报错，不能据此推断正式游戏的跨职业回退规则。

实现与证据分开维护，不能把这些假设或内部测试写成官方校准通过。六职业仍是完整目标；六职业士兵基础分支不代表全部巨型主体、死亡之翼与正式卡池完成。

## 公共效果与数据声明

[herald.py](../hs_sim/engine/herald.py)提供：

```python
Herald(player_id, source_id=None, grant_keywords=())
herald_count(state, player_id)
herald_rank(count)                    # 0、1、2，最高等级封顶
herald_multiplier(state, player_id)   # 1、2、4；供后续条件/选择分支读取
```

效果可由战吼、法术、亡语、地标或其他明确的能力调用。Keyword.HERALD 是声明，不自动执行；反制的法术不执行效果，直接召唤带战吼的卡不执行战吼。满场时保留本次使用事实但不制造士兵实体；缺失职业映射、非法来源或反应失败由事务统一回滚。

`CardDefinition.herald_scaling=True` 仅用于应强化的普通士兵/附肢，不用于巨型主体、组合模板或任意旧版巨型。士兵另声明 `herald_soldier_for=CardClass.WARRIOR` 等映射；每个注册表同职业仅允许一个士兵定义。其他职业分支尚未实现时禁止拿战士士兵代替。

每次 `HeraldRecord` 保存序号、玩家、来源、当时英雄职业、士兵卡面/实体、此前次数、生成等级、回合和动作。玩家计数从该历史计算，避免独立计数器与记录不同步；不要求卡组里有对应巨型或死亡之翼。普通出牌历史与兆示历史互不代替。

有场位时，新士兵放在仍在己方场上的效果来源右侧；法术、武器、死亡来源等放到右端。实际位置、来源在反应中离场等特殊情形由 R-069 跟踪。灼烧掠夺者的突袭通过后续 GrantKeyword 赋给这次生成的实体，不能误授予另一个士兵。

## 实体强化与生命周期

`Entity.herald_rank` 保存入场时捕获的等级，`DeathRecord` 也保存该等级。攻击/生命强化以有序普通附魔施加，效果数值通过 `instance_multiplier` 读取捕获实例；不反复读取玩家当前次数来改变老士兵亡语。只强化印刷属性，其他手牌增益保持原值。

| 来源/操作 | 内部契约 |
| --- | --- |
| 普通召唤、候选召唤、巨型附肢 | 创建时捕获当前召唤方进度，随后结算召唤反应 |
| 手牌/牌库中的士兵或附肢 | 尚未入场的基础卡不提前固定等级，入场时再应用 |
| 物理手牌/牌库召唤 | 原实体入场后捕获一次，保留已有一般属性增益 |
| 当前状态复制 | 复制捕获等级、属性附魔及能力；不再次加倍 |
| 基础复制、变形成附肢 | 按新实体/形态控制者的当前进度建立 |
| 转控 | 原有属性和捕获等级保留；不增加新控制者兆示次数 |
| 沉默 | 删除强化属性附魔和原有能力；玩家计数不受影响 |
| 回手后重打 | 重置旧捕获状态，按再次入场时的进度建立 |
| 复生 | 新建基础实体并应用当前强化，最后保留一血 |
| 巨型主体死亡/转控 | 附肢独立保留；规则与巨型公共生命周期一致 |

等级、历史和公开次数进入快照及哈希。schema 74 明确拒绝旧 1～71；外层 replay schema 仍为 1。恢复检查记录类型、顺序、计数连续性、职业映射、来源/士兵身份和实例等级范围。校验保证这些结构契约，不代表能认证任意一致重写后的对局历史。

## 2026-11-02 跨职业兆示：R-070修订与暂行差异

本节取代上文R-070中“仅用当前英雄职业、非兆示职业报错”的历史政策；其余等级、生命周期和计数窗口保持。适用于当前core-effects-v863 / snapshot schema680，不将旧存档静默补绑。

[开发者答复转录](https://hearthstone.wiki.gg/wiki/Herald)支持本人职业、单职业来源、对手的选择顺序；[玩家的伪装大师实测](https://www.reddit.com/r/hearthstone/comments/1sm0nns/fyi_if_you_start_the_game_as_another_harold_class/)支持开局绑定不随揭露职业改变。[官方公告](https://hearthstone.blizzard.com/en-gb/news/24245219/deathwing-strikes-back-in-cataclysm-hearthstone-s-next-expansion)仅证明六职业和一般机制；前两者不等同当前国服逐事件认证。[早期转载](https://www.gamersky.com/handbook/202603/2103959.shtml)包含未绑定无效果及入手绑定线索，不能据其认定当前正式计数和接受窗。调查材料见[原收据](../outputs/herald-class-resolution-20261102-01/assessment.json)。

每名玩家独立保存PlayerState.herald_class。战士、恶魔猎手、萨满、潜行者、死亡骑士和术士为兆示职业。选择顺序：

1. 本人已有绑定，始终保留。
2. 本人当前英雄属于六职业之一。
3. 原效果来源卡面的印刷元数据只有一个职业，且属于六职业之一。
4. 对手已有绑定，否则对手当前英雄所属的兆示职业。
5. 仍未确定则按用户授权暂不生效，不随机指定默认职业。

普通场景与正式开局共用初始化：起始英雄属于六职业则立即绑定；其他玩家在第一次实际执行并接受有效Herald时绑定。满场仍接受并计数，不制造士兵。换英雄保留已有绑定及次数；源牌职业不会覆盖已有绑定。request_from_context(c, grant_keywords=())捕获原战吼、施法、出牌或亡语卡面；源实体后续变形不改原面，复制/转移亡语按原能力来源卡面及实际亡语控制者处理。其他入口可使用Herald(player_id, source_id=None, grant_keywords=(), source_card_id=None)；原卡面必须有物理来源，未知来源/适配仍明确报错。

HeraldRecord分开保存当时hero_class与实际herald_class，校验起始绑定、记录绑定、次数/等级及士兵映射；非起始职业的后续绑定必须有已接受兆示。绑定随快照、clone、待选恢复、回放和普通事务一起保存或回滚，不加入玩家私有状态投影。该校验检查内部一致性，不认证外来未签名存档来源。

**待验证差异保留：**

- 双方均无可用绑定/职业，且原来源也不能确定职业时，本地Herald不召唤、不增加兆示次数、不提交兆示事件，也不分配实体或消耗随机数；同一主体的其他效果继续。用户已授权这一暂行行为，当前正式国服的计数细节仍待确认。

- 原R-069时序及其他既有待校准规则继续保留。缺少已确定职业的士兵适配器仍为错误，不进入无效果分支。
