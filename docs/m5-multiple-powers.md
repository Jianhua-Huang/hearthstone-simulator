## 范围与依据

传统构筑的第二英雄技能是明确的机制需求。[官方 35.6 公告的构筑资料片介绍](https://hearthstone.blizzard.com/en-us/news/24276665)提到第二技能；冻结本地记录 `JAIL_446` 鲜血医师萨安娜的中英文文本声明获得消耗残骸的第二技能，见[候选摘录](../outputs/v67-multiple-power-candidates.json)。这些依据支持建立公共能力，不足以确认重复获得、槽位上限、替换及所有刷新规则。公告同页酒馆段落不用于推断构筑规则。

本批完成独立实体和位置、安装、手动动作、费用/次数、常规被动监听、玩家观察及恢复。没有将 JAIL_446 适配为真实卡；必要测试使用合成定义和已有实验技能。正式来源的特殊策略仍归后续步骤。

## 状态与安装

- `PlayerState.hero_power_id` 始终指主技能，可为空。
- `additional_hero_power_ids` 是额外技能的有序物理实体列表。`hero_power_ids` 是只读派生元组，主技能在前，额外技能按安装顺序排列；不再存储一份重复权威列表。
- 实体 ID 标识技能，列表索引不作为持久身份。相同定义可以有不同实体，各自持有附件、费用、使用次数和入场修订。技能不占随从位置，不成为普通手牌。
- `PlayerSetup(additional_hero_power_card_ids=(...))` 明确构造实验初始状态；不会改变普通构筑的初始主技能绑定。
- `AddHeroPower(player_id, card_id, source_id=None)` 新建并追加一个额外技能，发出公开的 `hero_power_added`；安装本身不支付技能费用、不消耗使用次数、不执行技能效果。未知定义、错误类型或不存在的显式来源报错并回滚。

主位空缺不会将额外技能自动提升到主位。通用列表可以表达多个额外实例，**这不是对官方可同时拥有技能数量的承诺**，也不等于正式“获得第二技能”的重复安装策略。指定替换已在 12d-02 实现，上限及同名去重仍须正式来源契约明确；当前 AddHeroPower 按字面追加，不静默猜测应替换哪个技能。

## 手动使用与费用

已有 `UseHeroPower(player_id, entity_id, target_id)` 接收该玩家任一已安装技能。校验、目标查询和合法动作枚举使用同一派生列表；对手技能和墓地旧技能不能使用。动作 JSON 不变，`power` 仍是观察中的实体句柄，不用主/副按钮编号推断来源。

每个实体单独执行 `use_limit` / `uses_this_turn`；玩家的 `hero_power_uses_this_turn` 统计本回合所有手动技能使用的总数。各技能使用同一费用报价/支付系统，局部费用修正只作用于指定实体；“下一次技能减费”之类玩家修正由实际先使用的技能消费。目标、场位和使用条件逐技能判断，被动技能不能手动使用。

回合边界按既有约定清零双方所有已安装技能的次数及玩家总计。激活历史保存具体实体 ID、卡牌 ID、支付方式、局部此前次数和玩家此前总数，因此同名技能的记录也不会合并。选择和未完成效果沿用该来源，恢复后不改为主技能。

## 被动监听与既有主位操作

事件捕获遍历所有已安装技能，沿用控制者、入场顺序与实体 ID 的排序。`CheckHeroPowerTrigger` 复核实体仍处于该玩家技能集合、区域修订、入场身份与能力实例；恢复的监听帧同样校验。12d-02 已验证移除/重装及已开始选择的生命周期，见 [后续契约](m5-power-lifecycle.md)。

上述四种技能操作在 `power=None` 时读取主位，12d-02 已增加捕获引用的定向操作；灌注仍遵循主位契约，名称不隐含“对所有技能”。主位替换不误清空额外列表，缺少主位的间接触发保持报错，不随意选第一个额外技能。英雄替换现可显式保留/移除额外技能，具体正式卡牌的策略仍待证据。

## 玩家边界与恢复

观察保留 `hero_power` 主位字段，新增公开 `additional_hero_powers` 列表，包含现有技能 DTO 的费用、使用次数和被动标记。公开映射、只读条件上下文及玩家命令均能看到额外技能；不能因此访问对手隐藏手牌或全知状态。受限接口会检查额外技能的目标/使用条件可见性，不允许通过额外位置绕过 `unsupported_rule`。

快照严格要求新列表字段；拒绝非数组、布尔或非法 ID、重复占位、借用对手实体、区域不匹配和孤立技能。实体集合与列表的唯一位置约束复用原不变量。选择帧可保存尚未执行的 AddHeroPower，以及已激活额外技能的完成标记或被动监听。

[组合示例](../examples/multiple_hero_powers.py)将已有火焰冲击设为主技能、月亮的祝福设为额外技能。这是明确的实验场景，非合法开局声明。示例经玩家接口使用两项技能，在月亮待选时保存，恢复后完成选择、跨回合按相反顺序使用，并逐步回放比较：8 动作、31 事件。输出包括[快照](../outputs/multiple-powers-snapshot.json)、[回放](../outputs/multiple-powers-replay.json)和[玩家观察](../outputs/multiple-powers-view.json)。

## 技能安装与预选继承

AddHeroPower和ReplaceHeroPower增加事件前原子choose_branch；ReplaceHeroPower默认clear，显式inherit读取实际被选旧实体的保存配方。完整分支映射支持目标技能改变效果/价格/ID，保留普通/合并角色、来源范围与strict/override。需要原接受分支时显式capture_power_choose_branch再transfer_choose_branch，不能从当前物理配方或最近一次记录猜原根。

引用、主/额外位置、原费用/用途重置和已接受旧主体继续本页生命周期；失效引用不转向新技能，声明错误不因失效静默略过。窗口及字段见[公共契约](m5-choose-branch-producers.md)。当前开发prototype-v149/core-effects-v149、schema144/观察61，不把本页历史示例或旧验证冒作本版或国服证据，实际执行位置仍在两份主台账。
