## 声明与所属玩家

公共 [choose_policies.py](../hs_sim/engine/choose_policies.py) 提供 `AddChooseBothModifier`、`RemoveChooseBothModifier` 和不可变 `ChooseBothModifier`。政策使用全局附件分配器取得独立ID，保存所属玩家、原来源及卡面、创建回合、剩余用途和绝对回合期限。来源可以省略；提供来源时必须存在。来源离场、死亡、沉默、变形、转控或回手均不撤销已授予的玩家政策。明确移除、耗尽或到期才结束该实例；新授予得到新ID。

`uses=None` 为不限次数，`uses=1` 表达下一次，正整数可表达连续多次。`expires_turn=None` 无期限；其他值沿现有玩家次数政策的全局自然回合时钟，在该回合结束清理。主动结束能力不推进该时钟。到期反应中新授予的同回合政策仍进入公共到期稳定化，不能留到下一自然回合；无限重新授予由既有结算预算中止并回滚。

`kinds` 和 `origins` 明确适用范围，默认仅随从/法术的付费手牌根 `hand`。自动来源或英雄技能必须由调用者显式授权，不能从“下一张牌”自行扩大权限。支持的公共来源为：

| 来源 | 原接受窗及实际身份 |
| --- | --- |
| `hand` | 付款前冻结分支政策，原支付/提交证明保存后、承诺反应前一次消费；绑定实际 PlayRecord |
| `cast_effect` | 创建/取出实际法术后、分支/目标入口；绑定独立 effect cast |
| `cast_draw` | 抽到即施放的实际分支窗口；绑定实际 draw cast，原抽牌来源保持 |
| `cast_history` | 历史重施时的新窗口；绑定新 history cast，不借旧施法用途 |
| `physical` | 原 pre-child 窗口，在安装和入场反应前接受；绑定四个既有物理 profile 的实际 child |
| `power_manual` / `power_effect` | 自己的技能激活接受窗及 HeroPowerRecord；手动支付/次数与效果触发沿原入口 |

只支持现有注册门禁允许的抉择根种类。种类和来源必须各自非空、有序唯一且类型正确，来源须能匹配至少一个声明种类。未知范围、无效用途/来源/期限明确拒绝。政策没有给予新的英雄牌、武器、场地或其他特殊抉择根权限。

## 纯查询与一次接受

合法动作、目标、玩家命令预检仅查询政策，不创建收据、消耗用途或推动RNG。匹配玩家政策或原场上 `choose_both` 来源时，只开放定义声明的 combined 分支；combined 主体和目标由原抉择声明承担，不自动拼接普通分支，也不绕过目标/场地要求。

每个真实匹配根接受全部合格的玩家实例，即使场上来源或另一长期政策已经足以合并，也分别消费每个匹配的有限实例一次。不限次数实例保留。无抉择、不同种类、不同玩家或未授权来源不会消费。手动非法动作在接受前拒绝；后续异常沿公共事务恢复支付、用途、实体、事件和RNG。

原分支在接受后固定。施法重复、保留多个回溯结果、独立战吼/连击主体与它们的次数不额外消费这次抉择用途，也不按最新局面重选分支。回溯重试恢复原状态后重新接受一个尝试，最终保留的用途仍只扣一次。新的自动施法或新的物理 child 是新根，各按自己的新窗口接受。

当前明确采用“分支接受尝试”消费政策：已付费后反制、已接受的自动无目标失败和生成安装失败仍保留一次用途消费；执行前不合格的手动意图及整个事务异常不消费。这是可复核的本地政策，真实适配必须声明范围并经国服校准，不能套用到所有“下一次”来源。

## 原证明、恢复与信息边界

类型化 `ChoosePolicyReceipt` 保存原完整有序玩家政策、合格子集、原场上结构事实/合并来源、卡面、分支、实际根/来源、分配边界、时钟和原状态摘要。`ChoosePolicyProof` 在待结算的 `FinishChoosePolicy` 中保存完整原窗口，按同一纯生产者重算来源与政策；原窗口必须指向实际下一根。生成分支同时保留自己的请求、完整分支选项和RNG前后状态，新增玩家政策指针与完整原玩家政策，不能把玩家政策ID冒充场上附件。

消费先完成写入与收据，再捕获用途反应；剩余用途与历史链必须一致，不能复活已耗尽的ID、串玩家、借其他附件族、改原接受集合或截断原前缀。完成证明位于实际根工作之后，嵌套接受按实际内层先闭合；待选队列不得丢失、重复、提前或把完成控制塞入选择选项。终局先验证原队列，再保留一次消费并登记中断。

完整证明供恢复/回放与可信宿主内部使用。玩家观察仅给种类、来源范围、剩余用途和期限；用途事件同样是显式白名单投影。原来源ID/卡面、全局附件ID、原状态、候选/接受收据及RNG不进入玩家DTO。签名与来源认证不是本原型功能；紧凑终态记录证明内部一致性，不认证外部未签名存档的真实性。
