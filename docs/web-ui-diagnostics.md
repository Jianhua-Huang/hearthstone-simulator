## 查找一次慢操作

在 `client-8768.jsonl` 中查找卡牌名称或操作时间，再用该行的 `request_id` 查 `server-8768.jsonl`。两边均有同一个 `ui_id` 和请求编号。`at`/`received_at` 是带时区的 ISO 时间，服务端使用 UTC。

`request_started` 有记录但没有对应 `request_finished`，说明没有完成本次服务请求；浏览器会在发出请求前保存 `running` 标记及当前阶段，刷新后标记为 `interrupted`。这两种情况需要结合服务是否退出、请求是否取消判断，不能仅凭缺少结束记录断言引擎死锁。

主要字段含义：

| 字段 | 范围 |
| --- | --- |
| `command_submit_ms` | 原生玩家命令提交，包含协议/版本/合法性校验、引擎结算以及提交返回的玩家观察和事件；不是单独的 `Game.apply` 时间 |
| `legal_actions_ms` | 响应中重新生成合法操作，包含玩家观察与操作投影 |
| `events_ms` | 玩家可见事件投影 |
| `host_lock_wait_ms` | 等待宿主公共锁 |
| `route_ms` | 宿主路由总耗时，包含以上相关子项 |
| `serialize_ms` | 响应 JSON 编码 |
| `server_before_send_ms` | 准备发送响应头前的服务总耗时，不含完整响应写出 |
| `http_ms` | 浏览器请求开始到 JSON 解码完成；含宿主、传输和浏览器处理 |
| `intent_ms` / `outcome_ms` | 浏览器等待出手动画 / 结果动画完成 |
| `render_ms` | 根据回复更新页面的同步阶段 |
| `interaction_ms` | 本次提交开始至恢复输入后的总耗时 |

服务器总项包含子项，`http_ms` 包含服务器耗时，`interaction_ms` 又包含请求和动画，不能把所有字段相加。线程 CPU 计时受平台粒度影响，短请求可能出现 CPU 数字大于墙钟数字。浏览器记录页签在操作开始/结束时是否可见，有助于判断后台动画节流。

## 浏览器查看和导出

展开“调试详情 → 耗时诊断”，点击“导出耗时日志”。当前席位最近 150 条记录保存在该标签页的会话存储中，刷新仍保留，交接席位或新建对局时清空。旧服务不会收到不支持的遥测请求，浏览器导出仍可用于区分网络等待与前端动画。

客户端上报仅是诊断材料，不是引擎事实或回放证明。日志不保存授权令牌、AI 授权票据、完整命令、完整 DTO、全知快照或未公开的对手牌面；本地服务日志没有网页读取接口。日志写入失败只计数，不改变对局结果，浏览器上报也不阻塞出牌。浏览器显示“前后端已关联”表示收到新版服务的分段头；`persisted: true` 才表示该条前端记录已成功落盘。
